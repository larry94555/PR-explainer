# PR Explainer: Roadmap

This roadmap breaks the project into **milestones** and **PRs**.

- A **milestone** ends with something you can demo in an interesting way.
- A **PR** is a small change. Every PR is either **Small** (under 10 minutes to review) or **Medium** (under 20 minutes to review). If a PR grows past Medium while it is being written, split it before opening it.
- Every PR lists why it is needed, the problem it solves, the unit tests it adds, and step-by-step instructions for testing it.
- Every PR that changes something you can see (the popup, a badge, the toolbar icon, the settings page) includes screenshots of it in the PR description, saved under `docs/screenshots/pr-<number>/`, so a reviewer can see what to look for and where to find it.

## Technical choices

| Area | Choice | Reason |
|---|---|---|
| Extension platform | Chrome Manifest V3 | Required for new Chrome extensions |
| Language | TypeScript | Type safety across content script, service worker, and UI |
| Build | Vite, one entry per extension part, `manifest.json` copied from `public/` | Fast builds and a watch mode for reloading the extension, with no extra plugin while the manifest is static |
| Unit tests | Vitest + jsdom | Fast, works with TypeScript, can test DOM code against saved HTML fixtures |
| Local LLM | Ollama HTTP API (`/api/tags`, `/api/chat`) | Easy to install on a laptop, streams responses, many code models available |
| UI inside GitHub | Shadow DOM | Keeps GitHub's CSS from breaking our popup and keeps ours from breaking GitHub |

All calls to the LLM go through the extension's **service worker**, not the content script. That keeps the LLM address out of the GitHub page and avoids most CORS problems.

### Setup used by every "How to test" section
See [InstallingExtension.md](InstallingExtension.md) for a step-by-step version of steps 1, 3 and 4, including how to check out a PR's branch and how to confirm the extension loaded.

1. Install Node 22.22.2+ (or 24.15+) and run `npm install`.
2. Install Ollama and pull a model, for example `ollama pull qwen2.5-coder:7b`.
3. Run `npm run build` (or `npm run dev` for watch mode).
4. Open `chrome://extensions`, turn on **Developer mode**, click **Load unpacked**, and choose the `dist/` folder. After rebuilding, click the reload icon on the extension card.
5. Run `npm test` to run the unit tests.

## Milestone overview

| # | Milestone | Demo at the end |
|---|---|---|
| 1 | Extension skeleton | The extension loads, and a "PR Explainer active" badge appears on any GitHub PR page |
| 2 | Talking to the local LLM | The settings page lists your installed Ollama models and a **Test** button gets a reply from the model |
| 3 | Click-to-explain | Click a line in a PR diff and a popup explains what it does, why it's needed, and concerns |

| 5 | Chat box | Open a chat from the popup and ask follow-up questions about the code |

| 10 | Answers ready before you click | Open a PR, keep reading, and the lines you click are already explained: the toolbar badge shows how much of the PR is done, and a click on a done line is answered at once from the cache |

### PR 1.4: Message passing between content script and service worker (Small) ✅ Done
- **Status:** Done, merged in [#6](https://github.com/larry94555/PR-explainer/pull/6).
- **Why it's needed:** All LLM calls will run in the service worker, so the content script needs a reliable way to ask it for things.
- **Problem it solves:** Adds a small typed messaging layer in `src/messaging/`: `sendRequest(type, payload)` for the content script and a `MessageRouter` handler registry for the service worker, with timeouts and error forwarding. Request types and their payloads and results are declared once in `protocol.ts` (types only, so the content script still builds without shared chunks). Adds a `ping` message as the first use, and the badge tooltip shows whether the service worker answered.
- **Unit tests added:** `messaging.test.ts` uses a fake `chrome.runtime` to check that requests reach the right handler (sync and async), that handler errors come back as rejected promises with their name and message, that unknown types are rejected, that a missing listener or a failing `sendMessage` is reported, that timeouts fire, and that messages from other extensions or without our tag are ignored. `badge.test.ts` checks the new status line in the tooltip.
- **How to test:**
  1. Build and reload the extension (see [InstallingExtension.md](InstallingExtension.md)).
  2. Open a PR page.
  3. Hover the badge and confirm its tooltip says "Service worker: connected" (it sends `ping` on load).
  4. In `chrome://extensions`, click **service worker** under the extension to open its console, reload the PR tab, and confirm a `ping received` log line.

## Milestone 2: Talking to the local LLM

**Demo:** Open the extension's settings page. It shows the Ollama URL, a dropdown filled with your installed models, and a **Test** button. Click it and see a short reply from your local model. Stop Ollama and click **Test** again to see a clear "Ollama is not running" message with a fix.

### PR 2.1: Settings storage (Small) ✅ Done
- **Status:** Done, merged in [#7](https://github.com/larry94555/PR-explainer/pull/7).
- **Why it's needed:** The LLM URL, model name, and options must persist and be read from several places.
- **Problem it solves:** Adds `src/settings.ts` with a typed `Settings` schema, defaults (`http://localhost:11434`, no model, temperature 0.2, max response length 1024 tokens), `getSettings()`, `saveSettings(partialUpdate)`, and `validateSettings()`. The URL must be `http://` or `https://` on `localhost`, `127.0.0.1` or `[::1]`, with no path. Only values the user saved are stored, in `chrome.storage.sync` with one key per field (`settings.model` and so on), so a save writes only the fields it changes and two pages saving different fields at once can't overwrite each other. A bad stored value falls back to its default. Dev builds expose `debugSettings` in the service worker console for manual testing.
- **Unit tests added:** `settings.test.ts` with a fake `chrome.storage` covers defaults on first run, saving and reloading, merging partial updates, two overlapping saves of different fields both surviving, storing only saved fields, trimming input, rejecting invalid URLs (remote, LAN, lookalike hosts, paths, other schemes) and out-of-range temperatures and response lengths, storing nothing when a save is rejected, and falling back to defaults for bad stored values.
- **How to test:**
  1. Run `npm test` and confirm the settings tests pass.
  2. Run `npm run dev`, wait for `built in`, then reload the extension (see [InstallingExtension.md](InstallingExtension.md)).
  3. On `chrome://extensions`, click the **service worker** link on the PR Explainer card and use the **Console** tab of the DevTools window that opens.
  4. Run `await chrome.storage.sync.get(null)` and confirm it is `{}` (defaults live in code).
  5. Run `await debugSettings.get()` and confirm the defaults, then `await debugSettings.save({ model: 'qwen2.5-coder:7b' })` and `await debugSettings.save({ llmUrl: 'http://example.com' })` (the second is rejected).

### PR 2.2: Ollama client: list models and non-streaming chat (Medium) ✅ Done
- **Status:** Done, merged in [#8](https://github.com/larry94555/PR-explainer/pull/8).
- **Why it's needed:** The extension needs one place that knows how to talk to the local LLM.
- **Problem it solves:** Adds an `LlmClient` interface (`src/llm/types.ts`) and an `OllamaClient` (`src/llm/ollamaClient.ts`) with `listModels()` (calls `/api/tags`) and `chat(messages, options)` (calls `/api/chat` with `stream: false`, passing temperature and max response length as Ollama's `temperature` and `num_predict`). Every failure becomes an `LlmError` with a `kind`: `connection`, `model-not-found`, `origin-blocked`, `no-model`, `bad-response`, `http`, or `aborted`, which PR 2.4 turns into friendly messages. `createLlmClient(settings)` builds the client from the saved URL. Adds `host_permissions` for `localhost`, `127.0.0.1` and `[::1]` (any port), the same hosts the settings accept. Keeping it behind an interface makes it possible to add other local servers (such as LM Studio) later. Dev builds expose `debugLlm` in the service worker console.
- **Unit tests added:** `ollamaClient.test.ts` with a mocked `fetch` covers parsing the model list, building the chat request body, parsing the reply, and raising typed errors for connection refused, HTTP 404 (model missing), HTTP 403 (CORS or origin blocked), other HTTP errors, bad JSON, a missing model name, and a cancelled request. `manifest.test.ts` checks the new host permissions.
- **How to test:**
  1. Run `npm test` and confirm the `ollamaClient` tests pass.
  2. Make sure Ollama is running (`ollama list` works) and note one model name. Ollama refuses chat requests from extensions unless `OLLAMA_ORIGINS` allows them, so set it to `chrome-extension://*` and restart Ollama (on macOS: `launchctl setenv OLLAMA_ORIGINS "chrome-extension://*"`; on Windows, in Command Prompt: `setx OLLAMA_ORIGINS "chrome-extension://*"`; then quit Ollama and open it again).
  3. Run `npm run dev` (not `npm run build`, which leaves the debug helpers out), wait for `built in`, then reload the extension (see [InstallingExtension.md](InstallingExtension.md)).
  4. On `chrome://extensions`, click the **service worker** link on the PR Explainer card and use the **Console** tab of the DevTools window that opens (not the PR page's console).
  5. Run `typeof debugLlm` and confirm it says `'object'`. If it says `'undefined'`, `dist/` is a production build: run `npm run dev` and reload the extension again.
  6. Run `await debugLlm.listModels()` and confirm your models are listed.
  7. Run `await debugSettings.save({ model: '<a model from step 2>' })`, then `await debugLlm.chat('Reply with OK')` and confirm the reply.

### PR 2.3: Settings page UI (Medium) ✅ Done
- **Status:** Done, merged in [#9](https://github.com/larry94555/PR-explainer/pull/9).
- **Why it's needed:** Users need a way to point the extension at their LLM and choose a model without editing code.
- **Problem it solves:** Builds the options page (`src/options.html`, `src/options/optionsPage.ts`): URL field, model dropdown filled from `listModels()` (with a **Refresh** button, and reloaded when the URL changes), temperature slider, max response length, **Save**, and **Test connection** (sends "Reply with OK" using the values in the form, saved or not, and shows the reply and response time). Each invalid field shows its own error, and nothing is saved until all are valid. A saved model the server does not have stays selected and is marked "(not installed)". The page calls the LLM client directly: it is an extension page with the same host permissions as the service worker, and this keeps the typed `LlmError` for PR 2.4. Errors show the raw message for now; PR 2.4 makes them friendly.
- **Unit tests added:** `optionsPage.test.ts` (jsdom, against the real `options.html`) covers loading saved values into the form, filling the dropdown from a mocked model list, the "Choose a model" placeholder, keeping a saved model that is not installed, the "no models" hint, a failed model load, reloading models when the URL changes, ignoring a stale model list (including after the URL is changed to an invalid one), showing a validation error for a bad URL, saving (by method and by the **Save** button), per-field errors with nothing saved, and showing the test reply and time or the error text.
- **How to test:**
  1. Run `npm test` and confirm the `optionsPage` tests pass.
  2. Make sure Ollama is running and allows the extension (see step 2 of PR 2.2: `OLLAMA_ORIGINS` set to `chrome-extension://*`, then restart Ollama).
  3. Run `npm run dev`, wait for `built in`, then reload the extension (see [InstallingExtension.md](InstallingExtension.md)).
  4. Open the settings page. Either copy the **ID** from the PR Explainer card on `chrome://extensions` and open `chrome-extension://<ID>/options.html` in a new tab, or click **Details** on the card and scroll to the very bottom (below **Site access** and **Allow in Incognito**) to the **Extension options** link.
  5. Confirm the dropdown lists the models from `ollama list` and the status says how many were found.
  6. Pick a model, click **Save**, reload the page, and confirm the choice was kept.
  7. Click **Test connection** and confirm a reply such as "OK" and a time in milliseconds.
  8. Change the URL to `http://example.com` and click **Save**: confirm the URL error appears and, after reloading, the old URL is still there.

### PR 2.4: Friendly LLM error messages (Small) ✅ Done
- **Status:** Done ([#10](https://github.com/larry94555/PR-explainer/pull/10)).
- **Why it's needed:** The most common first-run problems are "Ollama isn't running", "model not pulled", and "origin blocked". Users need to know how to fix them.
- **Problem it solves:** Adds `describeLlmError(error, context)` (`src/llm/describeLlmError.ts`), which turns each `LlmError` kind into a short message and a fix, for example "Start Ollama (open the Ollama app, or run `ollama serve`)", "Run `ollama pull <model>`, then click Refresh", or the `OLLAMA_ORIGINS` command for the user's system (`setx` on Windows, `launchctl setenv` on macOS, a generic hint elsewhere, picked from the browser's user agent). Unknown errors get a generic fallback. The settings page uses it for **Refresh** and **Test connection** failures, showing the fix on its own line with commands as code.
- **Unit tests added:** `describeLlmError.test.ts` checks the message and fix for each error kind (with and without a known URL or model), the `OLLAMA_ORIGINS` command for each platform, the generic fallback for unknown errors, and platform detection from user agents. `optionsPage.test.ts` now checks the friendly text for a failed model load, a failed test, and a blocked origin on Windows.
- **How to test (Windows 11, Command Prompt):**
  1. Run `npm test` and confirm the `describeLlmError` and `optionsPage` tests pass.
  2. Run `npm run dev`, wait for `built in`, then reload the extension (see [InstallingExtension.md](InstallingExtension.md)) and open the settings page (see step 4 of PR 2.3).
  3. Stop Ollama: right-click the Ollama icon in the system tray and choose **Quit Ollama** (or run `taskkill /F /IM "ollama app.exe"` and `taskkill /F /IM ollama.exe`). ### PR 4.3: Explanation cache and Regenerate (Medium) ✅ Done
- **Status:** Done ([#19](https://github.com/larry94555/PR-explainer/pull/19)). Grew from Small to Medium because Regenerate needed the popup to go back to loading and the click handler to replace a running request.
- **Why it's needed:** Users often click the same line twice, and repeat requests to a local model are slow.
- **Problem it solves:** Adds a cache of finished explanations (`src/explain/explainCache.ts`) in the service worker, stored in `chrome.storage.session` so it survives the service worker going idle and is cleared when Chrome closes. Each entry's key is a SHA-256 hash of everything that shapes the answer: the PR (`owner/repo#17`, from the page URL), the model, the temperature and response limit from the settings, and the full prompt sent to the model (the instructions plus the file, line, and the code around it). The roadmap first planned to key on the commit SHA, but GitHub's diff pages do not show it reliably; keying on the code itself means a new commit that changes the code around the line is a miss, and one that does not touch it still hits. It keeps the newest 100 entries and drops the oldest first; a hit counts as new again. Only finished answers are saved, never errors or stopped replies. A broken or full cache never breaks an explanation: a failed read is a miss and a failed write is ignored. ### PR 6.3: Expanded file context (Medium) ✅ Done
- **Status:** Done ([#27](https://github.com/larry94555/PR-explainer/pull/27)).

## Milestone 8: Optimize LLM latency

**Goal:** an explanation finishes in **under 10 seconds**, measured from the click to "Answered in …" in the popup (the timer added in PR 3.5), on the laptop the extension is used on. If that is not possible on that hardware, find the lowest latency that is, and explain what limits it.

**Demo:** Run `npm run bench` and show the before and after table in `docs/latency.md`. Then open a PR, click a line, and watch the popup say "Answered in" with a time under 10 seconds (or at the floor the report predicts). Open the latency details in the popup to show where the time went.

**How the time breaks down.** Every Ollama reply reports `load_duration` (loading the model into memory), `prompt_eval_count` and `prompt_eval_duration` (reading the prompt), and `eval_count` and `eval_duration` (writing the answer). So:

> total ≈ load time + prompt tokens ÷ prompt speed + answer tokens ÷ generation speed + extension overhead

Each PR below attacks one term. Load time can be removed entirely by keeping the model loaded (8.3). Answer tokens are usually the biggest term, so 8.4 makes answers shorter. Prompt tokens are cut and cached by 8.5. Generation and prompt speed depend on the model and on whether it runs on the GPU (8.6). Prefetching (8.7) hides time the user would otherwise wait. The **floor** is the time for the smallest prompt and the shortest useful answer on the fastest model that still gives good explanations, with no load time. 8.8 measures it.

This milestone comes last because it builds on streaming (4.1, 4.2), caching (4.3), and the token budget (6.2). PR 8.1 and 8.2 only measure, so they can be done earlier if wanted.

## Milestone 9: Two-second answers

**Goal:** after a click, the popup shows the **whole** explanation within **2 seconds**, measured from the click to "Answered in …", on the laptop the extension is used on. The answer appears all at once instead of word by word. Every step of those 2 seconds can be seen: which tasks ran, how long each took, how many round trips went to the local LLM and to GitHub, and the prompt and reply of each one.

**Demo:** Turn on **Debug window** in the settings, open a PR, and click a line. The debug window lists every round trip the click made (to GitHub and to Ollama) with its prompt, reply and time, and the popup's **Details** shows a bar for each task. Then click lines and show the full answer appearing at once in 2 seconds or less, and run `npm run bench` to show the before and after table in `docs/latency.md`.

**Where things stand.** Milestone 8 brought the median from 94 s to 53 s on the test laptop (Windows 11, i7-1360P, `deepseek-r1:7b` on 100% CPU), with the first word arriving after 30 to 100 seconds. The popup itself opens at once in its loading state (PR 3.5); what takes 30 seconds or more is the first word of the answer, which is then written out at about 6.4 tokens per second.

**The arithmetic of 2 seconds.** From PR 8.1:

> total ≈ load time + prompt tokens ÷ prompt speed + thinking tokens ÷ generation speed + answer tokens ÷ generation speed + extension overhead

At 6.4 tokens per second, 2 seconds is about 12 tokens, so `deepseek-r1:7b` on this CPU cannot write a fresh answer in 2 seconds whatever the extension does. Each term needs to shrink:

- **Thinking tokens.** `deepseek-r1` is a reasoning model. It writes a hidden `<think>` section before the answer, and with the 300-token limit it often spent the whole budget thinking. This is very likely most of the 30 to 100 seconds before the first word. PR 9.1 measures it and PR 9.5 turns it off.
- **Answer tokens.** One sentence per section instead of two (PR 9.8).
- **Generation and prompt speed.** A 1.5B coding model usually writes four to five times faster than a 7B one on a laptop CPU. PR 9.9 points the Speed test and benchmark at 2 seconds and recommends such a model.
- **Overhead and round trips.** PRs 9.2 to 9.4 show every round trip and PR 9.7 removes the ones a click does not need.
- **Waiting at all.** Even a fast small model may take 2 to 5 seconds on a CPU for a fresh answer. PR 9.10 explains the changed lines on screen ahead of time, so most clicks are answered from the cache at once. PR 9.11 reports how many clicks meet 2 seconds both ways.

**Order.** The first four PRs only measure and show. They come first so each later fix can be checked in the debug window and in **Details**, one PR at a time. If the 2-second goal cannot be met for fresh answers on this laptop, PR 9.11 says what the floor is and what limits it, as PR 8.8 did.

### PR 9.7: Fewer round trips per click (Small) ✅ Done

### PR 9.10: Explain changed lines ahead of time (Medium) ✅ Done
- **Status:** Done ([#55](https://github.com/larry94555/PR-explainer/pull/55)).
- **Why it's needed:** On a CPU-only laptop even a small model may need a few seconds for a fresh answer. If the changed lines on screen are explained before they are clicked, most clicks are answered from the cache at once, well under 2 seconds.
- **Problem it solves:** A new **Explain ahead** setting (off by default, since it keeps the model busy and uses battery). When it is on, once the PR's **Files changed** tab has been still (no scrolling) for 2 seconds, the content script (`src/explainAhead.ts`) explains the added lines in the visible part of the diff (a changed line's new version is an added line), top to bottom, one at a time, using the same request a click would build (`lineRequest` from PR 8.7), so each answer goes into the cache from PR 4.3. The lines are found by a new `addedLineCells` in `src/diffDom.ts`, which works for both GitHub layouts, unified and split. It skips blank lines and lines that only close a block (`}`, `});`), and lines it already did on this page; a line already in the cache (from a click or hover) comes back at once and does not count toward the limit of 30 lines the model is asked about per page. It waits (checking again every half second) while a click's answer or a chat answer is being written, while the hover prefetch runs, and while the tab is hidden. A click or hover on other code stops the line being explained ahead, so the model is free for it, and puts that line back first in the queue; a click on the line being explained ahead joins it, as with hover. A failed line ends the pass (Ollama may be down) until the next scroll. Turning the setting or the toolbar button off, or leaving the page, stops it. Each page's lines share one debug log group, shown in the debug window as an **Explain ahead** group that fills in, and the popup's **Details** marks a joined round trip "by Explain ahead". ## Milestone 10: Answers ready before you click

**Goal:** open a PR's **Files changed** tab, keep reading, and find that most lines you click were already explained in the background, so the popup shows the answer at once from the cache. The background work goes through the whole PR, not only the lines on screen, starts with the code you are looking at, never makes your own click wait, and shows how far it has got.

**Demo:** Turn on **Prefetch whole PR**, open a PR with a few hundred changed lines, and watch the toolbar badge count up ("37%"). Scroll to a file further down, click a line, and the popup says "From cache" with an answer time well under a second. Click a line the background work has not reached, and it is answered fresh first, then the background work carries on. The debug window shows the queue: what ran, what is waiting, and what was cancelled for a click.

**Does the idea make sense?** Mostly yes, with two changes: one request per section instead of one per line, and one queue instead of many threads. Explaining lines before they are clicked is the best way to get instant answers on a CPU laptop: Milestone 8 showed a fresh answer there is limited by how fast the model writes, and the cache from PR 4.3 already makes a repeat click instant. PR 8.7 (on hover) and PR 9.10 (the changed lines on screen, one at a time, at most 30 per page) are small versions of it. This milestone grows that into the whole PR. Here is what holds up and what does not:

- **Memory is not the problem.** An answer is about 1 KB of text, so 2,000 of them are about 2 MB. Chrome's session storage, where the cache lives, allows 10 MB. But the cache today keeps only 100 entries and rewrites all of them on every save, so PR 10.2 changes how it is stored before it can hold a whole PR.
- **Several threads at once will not make it faster on this laptop.** The work is not done by the extension, it is done by Ollama, and on a CPU every request shares the same cores and memory bandwidth. Depending on its version and free memory, Ollama runs one or a few requests at once (`OLLAMA_NUM_PARALLEL`). When it runs several on a CPU, each answer gets slower and the total number of answers per minute rises a little or not at all; each extra request also needs its own share of memory for its context. When it runs one at a time, the others just queue. Either way, your click would be stuck behind the background work, which is the opposite of what we want. So instead of one thread per section, the plan is **one queue with priorities**: sections still matter, because they are the unit of work and decide the order (code on screen and the line under the pointer first, then the code near it, then the rest), but by default only **one** background request runs at a time. PR 10.1 measures whether 2 at once helps on this laptop before any default is set, and a GPU may well do better.
- **One request per section, not per line.** Sections are the right unit, but for a different reason: a line's request repeats the instructions and the code around it, so 10 lines of one hunk would read nearly the same prompt 10 times. One request per diff hunk (a section of the diff) that answers every changed line in it reads that prompt once, and Ollama's fixed cost per request is paid once. PR 10.5 does this, and each line's part of the answer is saved under the same cache key a click on that line uses, so a click finds it. Answers written for a whole hunk may be a little less sharp than one written for a single line, so PR 10.5 compares them, and **Regenerate** always asks about the line alone.
- **The cache follows the code.** An answer's cache key is a hash of the exact prompt, which includes the line and the code around it (PR 4.3), so a new commit that changes the code gives new keys and an old answer is never shown for new code. Prefetching starts over for the parts that changed.
- **Your click always goes first.** When you click a line, any background request for a different line is cancelled at once, so Ollama is free for yours, and put back in the queue. A click on a line that is being explained right now joins it, as with hover.
- **Time is the real limit.** On this laptop `deepseek-r1:7b` writes about 6.4 tokens per second, so one answer takes about 20 seconds; a small model such as `qwen2.5-coder:1.5b` (PR 9.9) may take about 4 to 8 seconds. These are estimates; PR 10.1 measures them. At 5 seconds a line, a PR with 300 changed lines takes about 25 minutes, and a big PR can take hours. That is why order matters, why there is a per-PR limit, and why answering a hunk per request (PR 10.5) matters.
- **Prefetching hides the wait, it does not remove it.** The model takes just as long per answer; the work is done earlier, while you read. A click on a line it has reached is instant, and a click on one it has not reached is as slow as today (a little slower if a background request has to be cancelled first). It also keeps the CPU busy, which costs battery and turns the fan on, so it is **off by default**, has a per-PR limit, and pauses when the tab is hidden.
- **"As soon as the extension loads" means as soon as a PR opens.** There is nothing to explain until a PR's **Files changed** tab is open, and GitHub does not draw every file until you scroll to it, so PR 10.4 builds the requests for files that are not on the page from the PR's diff, which GitHub's API returns in one go.

**Why a new milestone rather than more of Milestone 9.** Milestone 9's goal is a 2-second answer, measured one click at a time, and PR 9.10 is the last piece it needs. Prefetching the whole PR has its own demo, its own settings and its own risks (battery, a busy model), and Milestone 9 can be finished and reported (PR 9.11) without it. This milestone starts after PR 9.10, and reuses its idle wait and pause rules instead of replacing them.

**Order.** 10.1 measures first, so the defaults are set from numbers. 10.2 and 10.3 are the building blocks (a cache that holds a PR, and the queue), with no change you can see. 10.4 and 10.5 build the work for a whole PR, one request per hunk. 10.6 and 10.7 turn it on and show it, and 10.8 reports the result. 10.9 keeps the answers after the browser closes, so a PR prefetched once stays done.

### PR 10.3: Background queue in the service worker (Medium)
- **Why it's needed:** Hover (PR 8.7) and Explain ahead (PR 9.10) each decide on their own when to send a request. With a whole PR to work through, one place has to decide what runs next, how many run at once, and what gives way to a click, and it has to be the service worker so two PR tabs do not each keep the model busy.
- **Problem it solves:** A new `src/explain/prefetchQueue.ts` in the service worker. A job is a request (for now one line, built as a click would build it; PR 10.5 adds whole hunks) with a priority: **click**, **hovered**, **on screen**, **near the screen** and **rest of the PR**. A job whose answer is already cached is skipped, and a second job for the same line is merged with the first and keeps the higher priority. It runs at most `concurrency` jobs at once (1 by default), highest priority first, then in the order the lines appear in the PR. A click always runs at once: it cancels the running background jobs for other lines (so Ollama is free), puts them back at the front of their priority, and joins a job for the same line instead of starting a new one. Jobs can be re-prioritised (when you scroll) and dropped for a tab or PR (when you leave it). A job that fails is tried once more later, then skipped. Hover and Explain ahead now hand their lines to the queue instead of running their own requests, and behave as before. The debug window shows each job's start, finish and cancel in a "queue" group.
- **Unit tests added:** `prefetchQueue.test.ts` (fake service worker, fake model) checks the priority order and the PR order within a priority, at most `concurrency` running (1 and 2), skipping cached lines, merging a duplicate line and keeping the higher priority, a click cancelling running background jobs and putting them back first, a click joining a job for the same line (one request, same answer), re-prioritising and dropping by tab and PR, a failed job tried once more then skipped, and two tabs sharing one queue. `prefetch.test.ts` and `explainAhead.test.ts` are updated to check hover and Explain ahead now go through the queue and still pass their old checks.

### PR 11.1: Start the request when the mouse goes down (Small)
- **Why it's needed:** An explanation starts on `click`, which fires only after the mouse button is released. Pressing and releasing takes roughly 100 to 200 ms, and that time is spent doing nothing. Starting on the press gets it back on every click that was not prefetched.
- **Problem it solves:** In `src/clickHandler.ts`, a `pointerdown` with the main button and no modifier keys on a diff line's code sends the same request a click would (`lineRequest`, so it uses the cache and joins a running prefetch, as in PR 8.7). The popup still opens on `click`, and joins the request already running. If the pointer moves more than 4 pixels before it is released (the start of a drag selection, PR 4.4), or is released somewhere else, the request is cancelled and nothing is shown. Clicks on the line number, links and buttons in the diff behave as before. The trace from PR 9.1 gains a **Pressed** mark, so **Details** shows how much earlier the request started.
- **Unit tests added:** `clickHandler.test.ts` (jsdom, saved diff fixtures, fake service worker) checks that a press sends the request and the click that follows opens the popup on that same request (one request, not two), that a drag past 4 pixels and a release elsewhere cancel it, that the right button, modifier keys and a press while turned off send nothing, that a cached line opens from the cache, and that a press joins a running hover prefetch. `trace.test.ts` checks the **Pressed** mark.
- **How to test (Windows 11, Command Prompt):**
  1. Run `npm install` if you have not since the last pull, then `npm test`. Confirm all tests pass. Run `npm run lint` and `npm run build` and confirm both succeed.
  2. Run `npm run dev`, reload the extension, tick **Debug window** in the settings, and open a PR's **Files changed** tab and the debug window.
  3. Press and hold the mouse on a line's code for about a second. Confirm the debug window shows the request started while the button is still down. Release and confirm the popup shows that request's answer, with one request in the debug window.
  4. Press on a line and drag across several lines. Confirm the request is cancelled and the **Explain selection** button appears as before.
  5. Open **Details** in a popup and confirm the **Pressed** mark comes before **Clicked**.

### PR 11.2: Explain on hover, on by default and quicker (Small)
- **Why it's needed:** Hover prefetch (PR 8.7) is the cheapest way to hide the model's time, but it is off by default and waits 800 ms, so most people never benefit from it, and those who do often click before it starts. Most people rest on a line for less than a second before clicking it.
- **Problem it solves:** **Explain on hover** becomes on by default, and a new **Hover wait** setting (300 ms by default, from 150 to 2000) replaces the fixed 800 ms. A user who already turned the setting off keeps it off. Hover still sends one request at a time and cancels it when the pointer moves to another line. It sends nothing while background work is paused for the battery (PR 11.3), while the model is not loaded yet (the warm-up from PR 8.3 is still running), or while the tab is hidden. Because a shorter wait means more cancelled requests, the debug window counts hover requests that were cancelled before they finished, so the default can be checked against real use.
- **Unit tests added:** `prefetch.test.ts` (fake timers) checks the new default and that a saved wait is used, that a saved "off" is kept, nothing during the warm-up, on battery or in a hidden tab, and the cancelled count. `settings.test.ts` checks the default and the range. `optionsPage.test.ts` checks the new field loads and saves.
- **Screenshots:** the **Explain on hover** and **Hover wait** settings, light and dark.
- **How to test (Windows 11, Command Prompt):**
  1. Run `npm install` if you have not since the last pull, then `npm test`. Confirm all tests pass. Run `npm run lint` and `npm run build` and confirm both succeed.
  2. Run `npm run dev`, reload the extension, and open the settings page. Confirm **Explain on hover** is ticked (if you never unticked it) and **Hover wait** is 300.
  3. On a PR, rest the pointer on a line for about half a second and then click it. Confirm the debug window shows one request, started before the click.
  4. Move the pointer quickly down 20 lines. Confirm at most one request runs at a time and the cancelled count goes up.
  5. Set **Hover wait** to 1000, save, and confirm a half-second rest no longer starts a request.

### PR 11.3: Pause background work on battery (Small)
- **Why it's needed:** Hover, Explain ahead and whole-PR prefetch keep the CPU busy, which drains a laptop battery fast and turns the fan on. Today the only way to avoid that is to turn them off and remember to turn them back on.
- **Problem it solves:** A new **Background work on battery** setting: **Pause** (the default) or **Keep going**. The content script reads the charging state with `navigator.getBattery()` (the service worker cannot) and tells the service worker when it changes. While on battery and paused, hover, Explain ahead and the background queue send nothing new and let a running request finish. Your own clicks and chat questions are never paused. The toolbar badge (PR 10.7) shows "⏸" with the tooltip "Background work paused: on battery". When the browser does not report a battery (a desktop, or a browser without the API), nothing is paused.
- **Unit tests added:** `batteryState.test.ts` (fake battery manager) checks charging, on battery, the change events, and no battery API. `prefetch.test.ts`, `explainAhead.test.ts` and `prefetchQueue.test.ts` check that each pauses on battery and starts again when plugged in, that a click still runs, and that **Keep going** never pauses. `settings.test.ts` checks the default.
- **Screenshots:** the setting, and the toolbar badge while paused, light and dark.
- **How to test (Windows 11, Command Prompt):**
  1. Run `npm install` if you have not since the last pull, then `npm test`. Confirm all tests pass. Run `npm run lint` and `npm run build` and confirm both succeed.
  2. Run `npm run dev`, reload the extension, and tick **Explain on hover** and **Debug window**.
  3. Unplug the laptop. Rest the pointer on a line for 2 seconds and confirm no request appears in the debug window and the toolbar badge shows the pause. Click the line and confirm it is still answered.
  4. Plug the laptop in and confirm hover requests start again and the pause goes away.
  5. Set **Background work on battery** to **Keep going**, unplug, and confirm hover requests are sent.

### PR 11.4: Skip generated and vendored files when explaining ahead (Small)
- **Why it's needed:** Many PRs change lockfiles, minified bundles, snapshots or generated code. Nobody clicks those lines, but whole-PR prefetch (PR 10.6) would spend a big share of its time on them, often more than on the code that matters, since a lockfile change can be hundreds of lines.
- **Problem it solves:** A new `src/explain/skipFiles.ts` decides which files background work skips: the files GitHub marks as generated (it reads `linguist-generated` and `linguist-vendored` from the repository's `.gitattributes` at the PR's head, fetched once per PR), and common patterns (`package-lock.json`, `yarn.lock`, `pnpm-lock.yaml`, `Cargo.lock`, `go.sum`, `poetry.lock`, `*.min.js`, `*.min.css`, `*.map`, `*.snap`, `*.pb.go`, `*_pb2.py`, `dist/`, `vendor/`, `node_modules/`). A **Skip in background** setting lets you add or remove patterns. Hover and your own clicks still work on these files. The prefetch progress (PR 10.7) counts only the files it will explain and says how many it skipped.
- **Unit tests added:** `skipFiles.test.ts` checks each default pattern, a `.gitattributes` with generated and vendored entries (and negations), a missing `.gitattributes`, the fetch happening once per PR, and added and removed patterns. `prefetchQueue.test.ts` checks skipped files are not queued, a click on one is still answered, and the progress count.
- **Screenshots:** the setting, and the progress tooltip with the skipped count.
- **How to test (Windows 11, Command Prompt):**
  1. Run `npm install` if you have not since the last pull, then `npm test`. Confirm all tests pass. Run `npm run lint` and `npm run build` and confirm both succeed.
  2. Run `npm run dev`, reload the extension, turn on **Prefetch whole PR** and **Debug window**, and open a PR that changes `package-lock.json` as well as some code.
  3. Confirm the debug window queues lines from the code files and none from `package-lock.json`, and the badge's tooltip says how many files were skipped.
  4. Click a line in `package-lock.json` and confirm it is still explained.
  5. Remove `*.lock` style patterns from **Skip in background**, save, reload the PR, and confirm those files are now queued.

### PR 11.5: Keep the background queue when Chrome stops the service worker (Medium)
- **Why it's needed:** In Manifest V3 Chrome stops an extension's service worker after about 30 seconds with no events, and can do so between two background jobs or while a long prompt is being read with nothing arriving yet. The queue from PR 10.3 lives in the worker's memory, so a whole-PR prefetch that takes half an hour would quietly stop partway and only start again on the next click or scroll.
- **Problem it solves:** The queue saves its jobs (the request, the priority, the tab and PR, not the answers, which are already in the cache) to `chrome.storage.session` whenever they change, and when the worker starts again it reloads them and carries on, skipping jobs that are now cached or whose tab has closed. A job that was running when the worker stopped is put back at the front. Each content script with background work also keeps a port open to the worker and reconnects it when it closes, which keeps the worker running while there is work and tells the page when it has restarted. The debug window shows "worker restarted, 12 jobs restored".
- **Unit tests added:** `prefetchQueue.test.ts` (fake `chrome.storage.session`, fake worker restart) checks that the queue is saved on each change, restored after a restart in the same order, a running job put back first, cached jobs and closed tabs dropped on restore, and nothing done twice. `port.test.ts` checks the content script reconnects after the port closes and stops once its work is done. `debugLog.test.ts` checks the restart entry.
- **How to test (Windows 11, Command Prompt):**
  1. Run `npm install` if you have not since the last pull, then `npm test`. Confirm all tests pass. Run `npm run lint` and `npm run build` and confirm both succeed.
  2. Run `npm run dev`, reload the extension, turn on **Prefetch whole PR** and **Debug window**, and open a PR with many changed lines.
  3. Once a few jobs are done, open `chrome://serviceworker-internals`, find PR Explainer and click **Stop**.
  4. Confirm the debug window shows the worker restarting with jobs restored, and the badge keeps counting up without a click or scroll.
  5. Close the PR tab, stop the worker again, and confirm no jobs for that tab are restored.

### PR 11.6: Ollama status banner that recovers on its own (Medium)
- **Why it's needed:** When Ollama is not running, every click and every background request fails with its own error (PR 2.4), which is noisy, and when Ollama comes back the page does not know until you try again. Starting Ollama after Chrome is a common case on a laptop.
- **Problem it solves:** The service worker keeps one **Ollama status** (up, down, or model missing), from the result of every request plus a cheap `/api/version` check. When it goes down, background work stops at once instead of failing line by line, and the page shows one slim banner over the diff with the fix ("Ollama is not running. Start it from the Start menu.") and a **Try again** button. While it is down the worker checks again after 2, 4, 8 and then every 30 seconds, and only while a PR tab is open. When Ollama is back, the banner goes away, the warm-up from PR 8.3 loads the model, and background work carries on. A click while it is down still shows the full error in the popup.
- **Unit tests added:** `ollamaStatus.test.ts` (fake timers, fake Ollama) checks moving between up, down and model missing from request results, the check schedule and its back-off, no checks with no PR tab open, and the warm-up on recovery. `statusBanner.test.ts` (jsdom) checks the banner shows once for every tab, its text for each status, **Try again**, that it goes when Ollama is back, and its label for screen readers. `prefetchQueue.test.ts` checks background work stops while down and resumes after.
- **Screenshots:** the banner for "not running" and "model missing", light and dark.
- **How to test (Windows 11, Command Prompt):**
  1. Run `npm install` if you have not since the last pull, then `npm test`. Confirm all tests pass. Run `npm run lint` and `npm run build` and confirm both succeed.

### PR 11.13: Chrome's built-in model as an optional fallback (Medium)
- **Why it's needed:** Installing Ollama and pulling a model is the biggest hurdle for a new user. Recent versions of Chrome include a small on-device model (Gemini Nano, through the Prompt API) that extensions can use, which keeps code on the laptop as Ollama does. It is experimental and smaller than a coding model, and only machines with enough memory and disk can download it, so it is a fallback to try, not a replacement.
- **Problem it solves:** A new `src/llm/chromeAiClient.ts` behind the `LlmClient` interface, so explanations and chat can use Chrome's built-in model. The settings page gets **Model server**: **Ollama** (the default) or **Chrome built-in**, which shows whether this machine can use it (available, needs a download with a **Download** button, or not supported, with Chrome's reason). When Ollama is not running and the built-in model is available, the error from PR 2.4 offers **Use Chrome's built-in model instead**. Prompts are the same, with the token budget from PR 6.2 set to the built-in model's limit. The privacy check from PR 7.4 is unchanged, since the model runs inside Chrome and the extension makes no new network requests; `PRIVACY.md` says so. If the Prompt API cannot be reached from the service worker, the client runs in an offscreen document.
- **Unit tests added:** `chromeAiClient.test.ts` (fake Prompt API) checks each availability state, a download with progress, a non-streaming and a streaming answer, **Stop**, the token limit, and errors mapped to `LlmError` kinds. `optionsPage.test.ts` checks the setting and its states. `errors.test.ts` checks the offer appears only when the built-in model is available. `privacy.test.ts` still passes unchanged.
- **Screenshots:** the **Model server** setting in each state, and an answer from the built-in model, light and dark.
- **How to test (Windows 11, Command Prompt):**
  1. Run `npm install` if you have not since the last pull, then `npm test`. Confirm all tests pass. Run `npm run lint` and `npm run build` and confirm both succeed.
  2. Run `npm run dev`, reload the extension, open the settings page and set **Model server** to **Chrome built-in**. Confirm it says whether this laptop can use it, and click **Download** if offered.
  3. Once it is available, click a line on a PR and confirm the popup names Chrome's built-in model and shows an answer.
  4. Set **Model server** back to **Ollama**, quit Ollama, click a line, and confirm the error offers the built-in model.
